# 做过哪些有技术挑战的工作
面试官：“请你讲讲在字节期间做过哪些工作，哪些是有技术挑战性的工作，请你展开介绍一下。”

回答:

“好的，面试官您好。我在字节这三年的工作，可以看作是一个从支撑核心业务到建设技术中台，再到探索业务创新的完整过程。

我一开始就加入了全球商业化的广告落地页系统团队，负责整个后端的研发。这个系统是 TikTok 全球非中国区广告链路的核心一环，可以说是广告主资金消耗的‘最后一公里’。我加入时，正值业务高速增长期，系统面临着巨大的挑战。在我负责期间，它支撑的年广告消耗达到了 19 亿美金，C 端核心接口的 QPS 峰值超过 10 万。

在这期间，我成长非常快，也带过两位同学一起工作。其中有两项工作，我认为最能体现我的技术挑战和成长，我想重点分享一下：一项是面向全球用户的多活架构演进，另一项是提升系统复用性和可维护性的 B 端平台化重构。”

1. 全球多活架构设计

问题: “首先是全球多活架构的演进。这个项目最大的挑战在于，我们的系统需要同时服务两种截然不同的场景：

B 端创编：QPS 在几十到几百，但业务逻辑重，需要读写数据库。广告主希望在任何地方都能快速、稳定地编辑广告。
C 端投放：QPS 高达几万甚至几十万，是纯读场景，并且对延迟极其敏感，要求 200ms 内必须返回。全球用户需要就近访问，以保证最佳体验。

传统的单机房架构已经完全无法满足高可用和低延迟的需求。我的解决方案是针对 B 端和 C 端的不同特点，设计了一套混合式的多活架构。

我的方案:
C 端 (读密集): 我们落地了单元化架构。通过在 EU、US、ROW 等地部署独立的服务单元，将用户流量就近路由，实现了流量和数据的闭环，彻底消除了读请求的跨机房调用，确保 P99 延迟在 200ms 以内。
B 端 (写密集): 我们采用了一写一读的多活模式。以新加坡(SG)为主写机房，美东(VA)为只读机房，数据库采用一主多从异步复制。所有的写请求都强制路由到 SG，保证了数据的强一致性，并避免了多主写入的复杂冲突问题。为了解决主从延迟导致的“读后写”问题，我们使用了写后短时读主库的策略。

技术挑战: 核心挑战在于 C 端依赖的单元化改造，以及 B 端主从架构下数据一致性的保证和机房 Failover 预案的设计。
这套架构上线后，我们成功支撑了后续新机房的快速扩展，并且在一次代号为 ‘Project U’ 的突发事件中，它强大的容灾能力保证了核心业务的稳定，这是一个非常有成就感的时刻。”


1. B 端服务平台化重构

问题: 随着业务从 3 个增长到 10 多个，B 端创编服务的代码充满了重复逻辑和硬编码，新业务接入成本极高（平均一个月），系统的维护性也难以得到保障。
我的方案:
我主导了这次重构，引入了整洁架构 (Clean Architecture) 的思想。
架构分层: 我将系统明确划分为领域层、应用层和接口适配器层。核心业务规则（如落地页的状态流转）被封装在稳定的领域层。
依赖倒置: 应用层依赖领域层，但领域层不依赖任何外部实现。这使得核心逻辑可以被不同的接入场景（HTTP, RPC, OpenAPI）高度复用。
接口统一: 在最外层，我设计了统一的接入中间件，负责鉴权、参数校验和协议转换，将外部多样的请求转换为内部统一的命令对象。
技术挑战: 最大的挑战是如何在不影响线上业务的前提下，识别并抽象出稳定的领域模型，以及如何管理各层之间的依赖关系，确保架构不退化。重构后，新业务接入周期缩短到了一周。


1. 近线编译消息链路优化

问题: 落地页需要异步编译，但业务增长导致消息队列常态化堆积（峰值超 3 万），编译延迟长达数十分钟，同时呢资源供给也存在紧缺。
我的方案:
引入延迟处理: 实现“懒刷新”机制，活跃落地页优先编译，不活跃落地页推迟编译。利用基于 Redis 的分布式锁 + 全局限流器防止重复发送消息，避免下游服务过载。
实现优先级队列: 将 MQ 划分为两个队列，确保核心业务的消息能被优先消费。
无状态设计+流量分片：将编译服务本身设计为无状态，保证可以水平扩展；通过流量分片，保证在同一个数据合规区内消息不重复消费。
优化编译任务耗时
技术挑战: 挑战在于如何设计一个既能削峰填谷，又能保证关键任务低延迟的综合性解决方案。最终，消息堆积减少了 90% 以上。


1. AB 实验平台建设

问题: 业务方需要高频地对落地页进行 AB 实验，但当时的开发模式是硬编码，效率低下且难以管理。
我的方案:
我主导建设了一个通用的落地页 AB 实验中台。
配置驱动: 我设计了一套标准的实验配置模型，让业务方可以在后台自助创建实验，无需开发介入。
分流：复用了公司的分流服务，直接接入即可
数据闭环: 该平台与公司统一的 AB 平台（Libra）打通，自动完成流量打标和数据回传至 Adlog，实现了从实验创建到数据分析的完整闭环。
技术挑战: 核心难点在于如何设计一个高效、灵活且能保证流量正交的分流引擎，并确保实验数据能被准确无误地采集和归因。平台支持了 40+ 业务实验的快速迭代。


1. 性能优化与稳定性建设

问题: 随着 C 端 QPS 增长到 10W+，服务出现性能瓶颈和偶发的内存泄露。
我的方案:
内存泄露排查: 通过线上 pprof 分析，定位到是某个第三方 JSON 解析库在特定并发场景下的内存回收问题，通过更换为 gjson 并封装池化对象解决。
CPU 性能优化: 在核心热点路径上，我们大规模应用了 PGO (Profile-Guided Optimization)，获得了 5-10% 的 CPU 性能提升。
缓存策略优化: 针对缓存击穿、雪崩等问题，我们应用了多级缓存（本地缓存 + 分布式缓存）、SingleFlight 和逻辑过期等组合策略，保障了系统的最终可用性。
技术挑战: 挑战在于如何使用系统化的工具（如 pprof）和方法，去定位和解决隐藏在海量请求背后的微观性能问题。最终，系统实现了 99.95%+ 的 SLA。
